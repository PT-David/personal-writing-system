规范包编写说明

供创建和维护规范包的 AI 使用，也供用户检查系统的组织方式。日常写作从 README.md 进入，无须每次重读本说明。

一、确定规范包的范围

一个规范包服务于一类明确的写作任务。先说明目标读者、写作目的、常见交付形式，以及哪些要求只适用于其中的特定任务。包名应当让人看出用途；一个面向个人操作说明的技术文档包，不应默认代表全部技术写作。

用实际稿件、用户反馈和已确认的写作选择形成内容。只建立当前有经验支持的规范包。新文类沿用这里的组织和维护方式，具体规则由相应写作任务积累。

区分以下三种内容：
- 可以复用的写作要求：放入适用规范包。
- 当前项目的事实、代码、素材、设定或一次性要求：留在项目资料或当前任务中。
- 尚未确认的新想法：保留在讨论或项目反馈中，注明待定，不进入生效规则。

用户对当前任务的明确要求优先于包内默认规则。一次临时例外不自动改变长期规范。已有授权足以确定范围时，直接完成更新；有实质性分歧时，先把需要决定的内容讲清楚。

二、建立文件和资料的对应关系

每个规范包使用两个固定入口，确有需要时增加补充文件。

1. 规范包/<包名>/使用规则.txt

这是写作时的主要入口，按以下次序编写：
- 适用范围：写给谁、解决什么任务，必要时说明范围边界。
- 本次所需资料：由任务提供哪些信息，缺项会影响什么。项目事实不能用历史案例代替。
- 阅读清单：哪些补充始终必读，哪些在明确条件下必读，哪些仅供参考。写出准确路径和触发条件。
- 写作规则：按读者理解或实际写作过程分组，使用清楚的标题、短段落和必要的例子。
- 交稿检查：只列本类写作中容易遗漏、且能实际核对的事项。

如果无需补充，直接说明主文件已包含全部规则。不要为了凑齐栏目增加空内容。

2. 规范包/<包名>/规则依据.txt

供新增、解释、合并或调整规则时查阅。按“使用规则”中的规则标题对应记录：
- 这项规则解决了什么实际问题。
- 依据位于哪个项目、哪个文件及具体段落，或来自哪项用户明确要求。
- 哪些结论已确认，哪些情况不适用；有必要时保留简短的修改前后对照。

多项规则可以共同指向一份来源，只记录必要的对应关系。来源随时可能变化时，注明其版本、日期或提交编号。

新对话不能访问的聊天记录，不可作为唯一依据。应保存理解结论所需的最小原文、反馈和背景，并说明来源；不要复制整段无关对话。缺少来源时如实标注缺项，不编造原文、用户认可或验证结果。

“规则依据”解释当前规则的来由，不承担历次修改日志。用户没有改动某一段，不代表已经明确认可它。稿件是 AI 草稿、用户修改稿还是已确认稿，应按实际情况说明。

3. 规范包/<包名>/补充/

只在主文件容纳不便或仅部分任务需要时增加。可以保存专题要求、格式模板、完整案例等，每个文件有明确用途。

必要要求必须写在主文件中，或被主文件明确列为相应任务的必读文件。参考案例只能帮助理解，不能暗藏交稿要求。“遇到问题时自行找案例”不能替代必读清单。

模板说明它适用的任务和需要替换的部分。案例说明最少必要背景、原表达的问题、修改理由及适用边界，使未接触原项目的 AI 也能理解。

4. 项目资料/<项目名>/

按项目分别保存材料。同一项目供多个规范包引用时，共用这一份资料，不按文类重复复制。

项目中放一份简短的“材料说明.txt”，列出本项目的用途、主要材料或外部位置、稿件状态，以及与写作经验有关的反馈。以能找到材料为准，无须为每个小文件建立复杂登记表。

其他文件按实际材料安排；数量多时，再按文稿、反馈、来源、代码或设定等用途分目录。文件和子目录的类型由项目决定，不要求所有文类采用相同素材结构。

只保留支持写作或规则依据所需的材料。已有代码仓库可记录地址、提交编号、文件路径及相关摘录；网页来源应记录标题、链接、发布或更新日期（可确认时）、访问日期和所支持的具体内容。摘录不能脱离原文语境。论文资料、故事设定等也应标明其版本和用途。

可以引用仓库外材料，但必须有清楚的位置和必要上下文。影响规则理解的关键反馈或片段，应在本仓库留下足够依据。无法访问外部材料时说明缺项，不假定已经读过。是否收入完整资料，按当前任务需求和用户授权决定。

原稿与修改稿等用于对照的材料可以同时保存。它们是不同的依据，不是整套规范的历史副本。

三、把写作经验整理成可执行的规则

1. 先理解问题，再决定是否增加规则。

从用户要求、稿件与反馈中识别实际问题。先检查现有规则是否已覆盖；如果只是执行时遗漏，改进表述、阅读要求或交稿检查即可，不再添加同义条款。项目事实发生变化，也不必改写作规范。

2. 每条规则说明适用情况和具体做法。

标题应简短、明确且不重名，便于在“规则依据”中引用。正文回答：什么情况下需要这样写、具体怎样写、要保留哪些关键信息。避免“注意逻辑”“提升质量”这类无法执行的要求，也不要为所有文类推定同一表达风格。

例子只在有助于消除歧义时保留。例中出现的命令、角色、变量或业务名称，必须给出理解该例所需的说明。能用通用描述表达时，优先去掉无关的项目专名。历史例子中的事实不得套到当前项目。

3. 让文本脱离原对话也成立。

规范文件直接说明要求和用途。删除“本轮”“第一步”“之前已经讨论”等指向失效对话的表述。某个项目的稿件确认状态、待办和写作计划，记录在对应项目或 PR 中。

使用清楚的分级标题、短段落、适量编号和空行。纯文本文件默认用 UTF-8，不依赖 Markdown 表格表达层级。无需为普通规则增加 JSON、生成脚本或重复的导出版。

4. 迁移旧规则时保留有效经验。

先按主题核对已有要求，再决定保留、合并、改写或移到项目资料。缩短文件不能导致有效要求丢失。删除规则应有理由，理由写在 PR；确有必要的适用边界继续留在“规则依据”中。

5. 共用规则在有实际需要时独立建立。

若多个包确实需要同一组规则，可以建立“规范包/共用_<主题>/”，仍使用相同的两个入口。需要它的包在阅读清单中明确列出共用包及适用条件，不把共用包设为所有写作的默认必读。

共用包保持主题单一，不再引用其他共用包。使用方需要哪些内容，就直接列出哪些包，避免层层追读。少量相似措辞不必立即抽成共用包。

若两个适用包对同一事项有不同要求，在主包中写明任务边界或取舍，不能让 AI 靠文件顺序猜测。用户需求仍无法确定取舍时，再就具体冲突询问。

四、按任务读取和使用

写作按 README 的流程选择包，并读取同一提交版本的规范内容。AI 应取得所需文件正文，不能把目录、摘要或搜索片段当成已读完规则。

当任务提供的信息已足够时，直接写作。缺少必要事实时先读取相关项目资料或向用户询问。与任务无关的文类、历史项目和全部依据文件无须一并加载。

写作过程中需要查案例时，按主文件给出的路径读取。取得新的项目事实后，应回到当前稿件核对相应内容；案例本身不构成当前项目事实的证据。

采用复制文本、附件或其他临时方式对接时，提供所选主文件、适用的必读补充和当前必要资料，并注明来源路径与提交版本。维护仍以仓库中的原文件为准，临时副本不单独发展成另一套规范。

仓库无法访问、文件缺失或读取不完整时，明确说出缺项和影响。根据用户提供的替代材料继续，不能宣称已经按未读取的规则完成检查。

五、维护时只改动受影响的内容

1. 先确定需要保留的经验。

优先在具有写作上下文的对话中完成归纳。对尚未决定的内容，先说明准备改什么、理由及影响范围；已经确认或明确授权的内容直接实施。不要把同步仓库变成逐文件重复确认。

2. 确定改动位置。

- 改一条写作规则：更新对应“使用规则”和必要的依据。
- 增加案例或模板：更新相关补充；仅在阅读要求变化时改主文件。
- 增加项目事实或素材：更新对应项目资料及材料说明。
- 新增规范包或改变其适用范围：同步 README 的规范包目录。
- 改变文件位置或名称：同时修复引用它的文件。
- 修改共用规则：检索明确引用该包的使用方，检查是否产生冲突。

旧项目原始依据通常保留原状，不为新规则倒改原稿。更正旧材料中的错误时，说明更正内容，避免原始反馈和后续判断混在一起。

不受影响的项目、依据和规范包不作连带改写。

3. 通过一个分支和 PR 交付。

开始修改前，读取目标文件及相关依据，记录默认分支的基线提交。一个已确认的修改任务使用一个工作分支和一个 PR，验收中的后续补改继续提交到原分支，由用户合并。

提交前检查默认分支是否有新变化。需要同步时保留他人的修改，核对冲突含义，不用旧文件整份覆盖新版。已有本任务 PR 时先读取其最新进度和提交，避免重复建分支或 PR。

PR 简要写明：为什么改、改了哪些内容、读写行为有什么变化、做了哪些检查、还有什么待办。历史由 Git 和 PR 保存；文件保持稳定路径，无须新增整套版本目录、保存回执或每次都生成完整压缩包。

需要恢复旧内容时，把所需内容作为一次新的修复提交，保留之后其他有效修改。

4. 支持跨对话和中断续接。

有上下文的对话如果不能写入仓库，应交付可执行的修改材料：目标仓库与文件路径、读取的版本、确认后的具体改动、原因、必要依据及新增素材。执行对话先核对仓库现状，只处理对应变更；确有缺项时说明。

较长的修改任务中，在形成可检查的阶段成果后及时提交到工作分支。可先开草稿 PR，完成后再转为待审。每次阶段提交后同步 PR 进度，记录已完成、待完成、已做检查和影响续接的必要决定。续接对话先核对 PR 与分支实际内容，再继续原任务。

临时交接进度放在 PR 中，不写进长期有效的规则文件。完成后将 PR 更新为准确的交付状态，删除已经失效的待办。

六、交付前检查

检查与本次改动有关的内容即可：

- 不依赖旧对话，新对话能否理解适用范围、规则、例子和材料位置？
- 主文件的必读要求是否明确，路径是否存在，所需规则是否都能被读到？
- 新规则是否有实际依据，是否与现有规则重复或冲突？
- 项目事实、用户明确反馈、AI 推断及待定建议是否区分清楚？
- 修改是否保留了原有有效要求，涉及的目录索引和引用是否已同步？
- 用户能否从差异和 PR 说明中看出改动原因及影响？

新建规范包时，用有代表性的实际任务检查规则是否可执行。已有原稿、反馈或修改稿时，优先用这些材料核对。实际试写与反馈用于判断需要调整哪里；只做了结构检查或场景推演，就如实说明，不把它写成已经证明写作效果提升。
