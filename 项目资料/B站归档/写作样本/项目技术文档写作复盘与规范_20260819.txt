B站项目文档重写复盘：问题、根因与后续写作规范
================================================

用途：
1. 记录本次 B站项目文档重写过程中反复出现的问题、具体表现和解决办法；
2. 作为后续继续修改 B站 Archive / Cleanup / Export 文档时的自审标准；
3. 作为以后 P站项目编写类似“脚本使用指南 / 操作流程 / 命令速查”时的经验参考；
4. 减少“先由 AI 写一版，再由用户逐句找遗漏、逐句纠正”的重复劳动。

这份文档不是固定写作模板。
它记录的是【写作判断标准、资料收集方法、常见失败模式和审稿流程】。
不同文档仍应根据自己的用途决定结构。


一、本次写作真正要解决的问题
==========================

这类项目文档需要同时做到三件事：

【完整】
以后隔几个月重新打开项目，不需要重新翻几十轮开发对话，仍能知道项目结构、数据库、配置、命令、状态、异常、历史设计和新增功能。

【易懂】
不能为了“精简”把关键因果压成一句结论，让读者自己继续推导；也不能为了“全面”写成论文、源码注释或口语化教学。

【可查、可操作】
TXT 格式简单，因此必须让人能快速扫到命令、参数、路径、状态、CLI、异常和下一步。

最终判断标准：
【以后真正使用项目时，不需要再问一次 ChatGPT 才能理解原文。】


二、最核心的失败模式：把“重写”误当成“摘要”
==========================================

这是本次最早出现、后来又多次复发的问题。

典型表现：
- Watcher 旧指南中大量目录、数据库、scan、故障细节被压成几句摘要；
- scan 原来解释数据来源、基线、分页、数据库写入和产物，新稿一度只剩命令；
- Archive 旧稿中 plan / batch / 数据库删除后果的大段经验，被压成几个定义。

问题不在于字数减少，而在于把帮助理解和操作的“桥接信息”一起删掉了。

错误思路：
“这几段能用一句专业定义概括，所以删掉细节。”

正确判断：
删掉以后，读者是否还知道：
- 为什么；
- 什么时候；
- 会发生什么；
- 下一步怎么办；
- 有哪些例外。

如果仍要自己推理，就不是精简，而是信息损失。


三、只写一级结论，不写直接后果
============================

这是反复最多的问题之一。

例 1：Watcher 重新 init

不充分：
“重新 init 会改变扫描基线。”

完整链条至少应说明：

重新 init
→ 重设基线
→ 清空最近 scan 时间
→ 下一次按首次扫描处理
→ 已有完成任务不会重复建任务
→ 如果新基线向前扩展，过去从未进入 watcher.db 的旧投稿会成为新的 PENDING
→ 后续可能真的下载到更早历史视频。

例 2：Archive 多 MP4

不充分：
“多个 MP4 可能是不同 P，也可能是历史不同清晰度。”

还应该解释：
如果同一投稿保存了不同清晰度，可能会重复上传；但本项目主要按标题检索，不按清晰度检索，因此这种重复在设计上可以接受。

例 3：Telegram 消息被手工删除

只写：
“数据库不会自动感知删除。”

还不够，应区分：
- verify 前删除：会影响核验、repair 或 run 状态；
- verify 后删除：数据库保留当时 VERIFIED 的历史状态，但远端事实已经改变，不会自动回滚。

【写作标准】
每写一个重要规则，都问：
“读者看完后最自然会继续问哪两三个问题？”
如果答案会影响执行、重试、删除、数据安全或历史状态，就应在当前位置回答。


四、旧稿不是单纯的“旧资料”，而是事故知识库
==========================================

旧文档中很多长段落，是因为过去真实遇到过问题才补进去：

- BVID 大小写；
- `.part` 断点污染；
- yt-dlp 成功但视频不完整；
- DownKyi 导入匹配；
- Archive batch 中断；
- verify 卡住；
- FloodWait；
- 源文件修改后旧 plan 无法恢复；
- 数据库恢复后历史状态倒退；
- 相册/媒体修复困难。

因此重写旧文档时不能只问：
“当前代码还有没有这个字段/命令？”

还要问：
“这段话当初为什么会被写进去？”

正确处理：
历史问题是什么
→ 当前版本是否还会遇到
→ 当前机制怎样解决
→ 旧操作是否废弃
→ 哪些经验仍应保留。

例如 Watcher 的 `current/failed_attempts`：
真正值得保留的是早期异常断点曾导致流程成功但媒体不完整，因此后来才把可信 current 和失败 attempt 隔离。

结论：
【旧稿既是旧说明，也是已经付过代价的经验记录。】


五、新功能必须单独做覆盖检查
==========================

反过来，旧稿也无法帮忙发现后来新增功能的遗漏。

Archive 后期新增：
- UID / 作者改名；
- 多 target；
- General 导航；
- 动态 ZIP；
- 作者名称历史；
- BVID 安全回填；
- early-interrupt；
- 新 Cleanup 边界。

如果只做“旧稿更新”，这些新功能很容易只写成一两段摘要。

例如 target 不能只列字段，还要说明：
- 它是 Telegram Forum 群；
- 群是谁创建；
- chat_id 怎么取得；
- target_key 谁定义；
- target_id 谁生成；
- 默认 capacity；
- 新作者怎样分配；
- 历史作者是否重排；
- 容量不足时是否部分分配；
- run/resume/verify/repair 怎样沿固化 target 工作。

以后至少独立做两项检查：

A. 【旧知识回收】
过去有价值的内容有没有丢？

B. 【新功能覆盖】
近期新增机制即使旧稿完全没写，新文档是否也能独立解释清楚？


六、代码覆盖完整，不等于文档内容完整
==================================

本次多次出现：
- 22/29 个子命令都写到了；
- argparse 参数机械检查没有漏；
- schema 表也列出来了；

但文档仍然“不够完整”。

原因：
【命令名存在 ≠ 命令已经被解释完整。】

例如 `mark-source-unavailable` 只有命令和状态变化，读者仍可能不知道：
- 什么时候用；
- 和 FAILED 的区别；
- STAGED 会怎样；
- scan 后会不会重新激活；
- 取消后怎么办。

`creator_key` 只说“历史业务键”，也会继续引出：
“现在新作者还生成 creator_key 吗？”

机械检查只能防止完全漏项，不能防止“话只说一半”。


七、命令章节的可发现性问题
========================

### 1. 独立命令不能藏在另一条命令下面

Watcher 的 `preview-creator` 曾被塞进 `init-creator` 正文。
逻辑上相关，但视觉上容易看漏，或误以为它只是 init 的参数。

解决：
独立命令一般有独立小标题；如果非常轻量，也要明显标成【补充：独立命令】。

### 2. 同一命令的主要参数不能散落全文

曾出现：
- `scan --details` 在 scan 主节；
- `scan --refresh-access` 藏在权限章节；
- `download --retry-failed` 到故障章节才第一次出现。

最终确定：
【主要入口集中，专题场景允许重复。】

scan 主节先集中列主要用法；
权限章节可以再次重复 `scan --refresh-access`，并说明为什么在这里使用。

这种重复是不同查阅路径的入口，不是无意义赘述。


八、命令说明应该有轻重
====================

复杂、高频、容易误用：
scan / download / run / resume-batch / verify-batch

应明显写得更细：
- 作用；
- 常用形式；
- 主要参数；
- CLI；
- 状态变化；
- 常见异常；
- 下一步。

低频简单命令可以短很多。

错误：
为了统一格式，每个命令固定“用途/参数/输出/异常/示例”。

正确：
统一的是【信息够用】，不是章节长相完全一致。


九、CLI 输出必须就地解释
======================

失败做法：
把所有 CLI 判断集中放在文末，每条命令只有一句摘要。

正确：
重要 CLI 放在对应命令附近。

例如 status：
UP主A｜投稿 10｜待下载 0｜失败 0｜DownKyi待补救 0｜已整理 10

随后解释：
- 待下载何时应为 0；
- FAILED 非 0 说明什么；
- MANUAL_FALLBACK_PENDING 下一步是什么；
- “投稿 10”是否等于账号历史总投稿。

核心命令不必贴整屏输出，只需展示真正影响判断的部分。


十、目录树、数据库和配置不能只列名字
==================================

目录树如果只列：
视频.mp4 / info.json / source.json

却不解释：
- source.json 保存什么；
- info.json 谁生成；
- 多 P 怎么放；
- 哪些文件程序依赖；
- 哪些只是给人看；

那么目录树只是视觉装饰。

数据库也不能只列表名。
至少应说明：
“这张表代表什么 + 保存哪些关键内容。”

配置也不能只写：
`download_workers：并发数`

还应根据重要程度说明：
- 当前默认；
- 调大/调小影响；
- 什么情况要改；
- 历史实测建议值（如有）。


十一、AI回答腔和无中生有的转折
============================

反复出现的句式：

“不是……而是……”
“重点不是只告诉……”
“你可以把它理解为……”
“本文用于……”
“Archive 的源目录不是 Watcher 临时目录，而是……”

这些句式不是绝对禁止。

合理：
- FAILED 和 VERIFY_REQUIRED 确实容易混淆；
- General 和客户端“全部”容易混淆；
- pilot 是真实上传，不是 dry-run。

不合理：
没人会把 Archive 源目录理解成 Watcher 临时目录，却强行制造对立。

判断标准：
【只有真实存在易混淆概念，而且误解会影响理解或操作时，才使用对比。】


十二、不要写 AI 习惯性废话
========================

Watcher Cookie 段落曾加入：
- “只安装来源可信扩展”；
- “Cookie 是登录凭据，不要公开分享”。

用户明确认为：
这种安全补充适合一般 AI 回答，不适合自己的长期项目文档。

同类元话语还有：
- “本文怎么使用”；
- “速查按实际顺序排列”；
- “如果只想看命令请看另一份”。

如果结构本身已经清楚，就不需要再解释结构。

【删减标准】
应该删除的是“不增加项目知识”的话，而不是技术细节。


十三、术语不能为了显得技术化而变模糊
==================================

例：

清楚：
“UP 名称、文件夹路径、主页 URL”

模糊：
“当前名称、folder_path、home_url”

源码字段并不天然更适合人读。

同样，项目长期叫“扫描基线”，就不要随意换成“扫描边界”。

Archive 中“同一逻辑投稿文件发生实际变化”也不如：
“已经上传的视频后来发生变化，scan 检测到后会生成更新版本并再次上传。”

原则：
- 数据库字段章节可以写字段名；
- 行为说明优先业务语言；
- 项目已有术语保持一致；
- 技术精确不等于变量名越多越好。


十四、混合情况、前提和时间顺序不能省略
====================================

### source.json 排序

只写：
- 无 source 按名称；
- 有 source 按时间；

虽然能推导混合情况，但仍应直接写：
如果一个 UP 同时有两类目录，先排无 source，再排有 source。

### Telegram 删除

必须分：
- verify 前；
- verify 后。

### plan 引用的源文件变化

不能只写：
“修改/删除会影响 resume。”

读者自然会继续问：
- 删除后从回收站恢复原文件呢？
- 重新下载同名文件呢？
- 大小一样但内容不同呢？
- 怎么修？

这些要在原处简要回答，或明确引到故障章节完整说明。

原则：
凡是结果取决于“什么时候做、之前是什么状态、恢复的是不是同一内容”，就必须把条件写出来。


十五、故障说明必须形成闭环
========================

失败示例：
“先看 download_logs，再 retry。”

问题：
看什么？看完说明什么？下一步做什么？

故障说明应围绕：

症状
→ 判断
→ 检查
→ 动作
→ 结果
→ 回到主流程哪一步。

例如 repair-media：

STAGED
→ audit 发现异常
→ repair-media
→ 异常文件进 quarantine
→ 状态变 PENDING
→ 重新 download
→ 再 status/audit。

这叫【故障处理闭环】。


十六、历史原因不能突然插入
========================

失败写法：
“0.1.x 旧版 downloaded/parts 位于 BVID 根目录……”

如果不解释为什么改，读者只会疑惑。

正确：
过去异常 `.part` 被继续当可信断点
→ 流程可能完成但媒体不完整
→ 后续把 current 和 failed_attempts 分开
→ 旧结构首次接管时自动隔离。

历史说明的价值是解释当前机制，不是展示版本考古。


十七、三种文档不能写成同一种文章
================================

【脚本使用指南】
目标：真正理解整个系统。
包括项目结构、机制、数据库、配置、命令、CLI、状态、异常、设计原因、历史兼容和新功能。

【操作流程】
目标：隔很久不用，也能照着一步步做完。
按真实执行顺序组织，保留关键命令、关键 CLI、常见分支和轻量删除判断。

【命令速查】
目标：已经知道要做什么，只想快速复制命令。
说明极短，同一命令主要参数集中，整体顺序贴近日常运行。

不能把使用指南缩短后直接当流程，也不能把命令列表加几句话就当指南。


十八、速查应按实际使用路径，而非单纯功能分类
==========================================

命令速查曾按：
scan / download / status → 作者 → 配置……

后来发现真实首次运行应先：
check-config
→ check-login
→ init-db
→ 作者同步/初始化
→ scan
→ download
→ status
→ 异常维护。

重新排序后又暴露另一个问题：
没必要在开头再写一段“本文件按实际顺序排列”。

经验：
【结构正确后，让结构自己说话。】


十九、TXT 的重点突出靠阅读层次，不靠固定模板
==========================================

可使用：
- 短标题；
- 空行；
- `【关键概念】`；
- 独立命令块；
- 目录树；
- a/b/c；
- `→` 因果链；
- 少量真正必要的“注意：”；
- 重要结论尽量放段落开头。

不能变成每节固定：

获取方式：
配置位置：
命令：
参数：
输出：
异常：

这又会成为另一种八股文。

目标：
【重要信息在长 TXT 中能被一眼扫到，但正文仍自然连贯。】


二十、“详见另一文档”不能代替本文件最低闭环
==========================================

下载流程曾只写：
“详细删除规则见项目文件与产物清理说明。”

但流程本身至少仍应告诉：
- 哪些现在可以删；
- 哪些不能删；
- `.part` 为什么不能清；
- 正式视频必须等 Archive verify。

分工应当是：

流程文档
→ 给当前操作所需的轻量判断。

产物说明
→ 解释完整生命周期。

Cleanup 指南
→ 解释自动审计和删除规则。

交叉引用不能成为省略必要内容的借口。


二十一、命令索引不能只是“防漏证明”
===============================

Archive v4 最后的索引只列：

check-config
check-target
scan
run
...

然后写“详细用途见前文”。

这对于真正查找命令帮助不大。

以后索引至少应给：
- 对应章节；
- 主要参数/用途的极短提示；
或
- 能直接定位正文的位置。

索引的作用是【查找】，不是证明“作者记得全部命令”。


二十二、为什么这些问题会反复出现
==============================

最值得沉淀的是根因。


### 根因 1：LLM 的摘要偏好

面对很长旧稿时，模型天然倾向：
- 合并相似段落；
- 用上位概念替代细节；
- 避免重复；
- 把长解释压成专业定义。

总结任务中这是优点；
长期技术知识迁移中却容易删掉边界和事故经验。

解决：
明确任务是【迁移 + 更新】，不是摘要。


### 根因 2：只做覆盖检查，不做问题闭合检查

看到：
- init-creator 写到了；
- target 写到了；
- creator_key 写到了；

就误以为完成。

解决：
每个重要机制做【二级疑问检查】。


### 根因 3：过度依赖当前代码

代码适合确认：
- 参数；
- schema；
- 状态；
- 当前行为。

但很难告诉：
- 为什么这样设计；
- 旧方案踩过什么坑；
- 哪个奇怪规则在解决什么历史事故。

解决：
资料必须同时包含：
【当前代码 + 旧稿 + 开发历史 + 最近变更材料】。


### 根因 4：把用户反馈当局部补丁

例如用户指出：
“preview-creator 不要藏在 init 里。”

如果只修这一处，没有抽象成：
“独立命令不能埋在另一命令章节”，
那么 Archive 或 P站还会再犯。

解决：
每次反馈都必须：
1. 修当前段落；
2. 更新全局审稿规则；
3. 用新规则重新扫描全文。


### 根因 5：机械防漏指标造成虚假安全感

“22 个命令全出现”
“29 个子命令全覆盖”
“所有参数无缺失”

这些只能防止完全漏项。

不能证明：
- 场景讲清；
- 后果讲清；
- CLI 好用；
- 历史保留；
- 重点易找。

解决：
机械检查是最后一层，不是质量判定。


### 根因 6：一次性长文缺少独立多轮审稿

第一次生成时同时处理：
结构、事实、语言、完整性、参数、历史。

容易顾此失彼。

解决：
交付前必须把不同目标拆成多轮审稿，而不是笼统一句“已自检”。


二十三、后续 B站/P站的正确写作流程
================================

### 第 1 步：确定文档类型

先明确：
使用指南 / 操作流程 / 命令速查 / 产物说明 / 故障记录 / 交接材料。

不要先套模板。


### 第 2 步：建立资料来源

A. 当前代码 / CLI / schema / config
→ 当前事实。

B. 原始旧文档
→ 已沉淀知识和使用经验。

C. 开发历史 / 交接材料 / 变更日志
→ 设计原因、新功能、踩坑。

D. 用户最新反馈
→ 写作标准和禁区。


### 第 3 步：先做内容资产盘点

列：
- 功能；
- 命令；
- 参数；
- 状态；
- 数据库；
- 文件；
- 配置；
- CLI；
- 故障；
- 历史事故；
- 新增机制；
- 废弃机制。

标记：
【当前】/【历史仍需保留】/【已废弃】/【待核实】。


### 第 4 步：旧知识回收

逐段问：
- 为什么存在？
- 当前还成立吗？
- 行为变了以后历史原因还值得留吗？
- 是否记录了事故经验？


### 第 5 步：新功能覆盖

根据最近开发版本单独列：
- 新增了什么？
- 旧稿有没有？
- 新稿是否把用途、结构、参数、状态、后果、异常讲清？


### 第 6 步：设计整篇结构

使用指南：
偏系统生命周期/认知结构。

操作流程：
偏真实执行顺序。

速查：
偏复制命令速度和实际运行顺序。


### 第 7 步：写正文时做因果闭环

重要功能内部至少检查：

执行/发生 A
→ 改了什么
→ 下一步会怎样
→ 历史数据怎样
→ 例外是什么
→ 出问题怎么恢复。

不要求写成固定标题，但答案必须存在。


### 第 8 步：核心命令入口集中

主要参数第一次出现时集中列出；
专题章节允许重复并深入解释。


### 第 9 步：CLI 就地解释

展示代表性输出；
告诉读者看什么、什么异常、下一步是什么。


### 第 10 步：至少做 7 轮独立审稿

A. 旧知识检查
B. 新功能检查
C. 二级疑问检查
D. CLI/命令检查
E. 当前代码事实检查
F. 语言风格检查
G. TXT 快速扫读检查


二十四、二级疑问检查法
====================

对于每个重要段落，强制问：

1. 这句话告诉了事实，但读者下一步会问什么？
2. 下一问是否会影响：
   - 是否执行；
   - 是否删除；
   - 是否重试；
   - 是否重新扫描；
   - 是否重复上传/下载；
   - 是否破坏数据库；
   - 是否影响历史状态？
3. 如果会，答案不能省略。

例：

“动态 ZIP 自动决定是否生成。”

下一问：
- 什么条件才生成？
- 少量增量为什么没有 ZIP？
- 没 ZIP 是否意味着漏上传？

这些都影响判断，因此都应该直接说明。


二十五、典型“错误 → 修正”示例
============================

### 例 1：过度摘要

差：
“Watcher 负责源端监测与下载，Archive 负责 Telegram 归档。”

改进：
“Watcher 负责识别本地需要监测的 UP、发现新增投稿并完成下载整理；Archive 从正式视频目录开始，负责生成上传计划、维护 Telegram 群组/话题、上传消息并记录核验状态。”

### 例 2：话只说一半

差：
“重新 init 会改变扫描基线。”

改进：
“对已有作者重新 init 会重设基线，并让下一次 scan 按首次扫描处理；已有完成任务不会重复下载，但如果新基线向前扩展，过去从未进入 watcher.db 的历史投稿会成为新的 PENDING。”

### 例 3：抽象词过重

差：
“同一逻辑投稿文件发生实际变化时建立新版本。”

改进：
“已经上传过的视频如果后来被本地新文件替换，scan 检测到内容变化后，会把它作为更新版本再次归档，旧 Telegram 版本仍保留。”

### 例 4：只给动作，不给用途

差：
“repair-media --bvid ... --apply”

改进：
“当任务已经 STAGED，但 audit-media 后来发现正式视频损坏时，用 repair-media 把异常成品移到 quarantine，并把任务重置为 PENDING；之后重新 download。”

### 例 5：命令索引敷衍

差：
“scan / run / verify / repair-item，详见前文。”

改进：
“scan → 第5章；常用参数：--details / --errors-only / --zip ...
run → 第8章；常用参数：--all / --creator / --order ...”

### 例 6：不必要转折

差：
“Archive 的源目录不是 Watcher 临时目录，而是……”

改进：
“Archive 使用的正式视频目录：F:\新建文件夹\b站视频”

### 例 7：重点埋在段落

差：
Cookie 长段落中顺带提到 Get cookies.txt LOCALLY。

改进：
让【Get cookies.txt LOCALLY】、实际保存路径和 `export-cookies` 命令在视觉上能快速扫到。


二十六、降低后续维护成本
======================

### 1. 每个事实设置“主要归属”

例如：
download_backend 完整定义在配置/下载机制；
故障章节只说明什么时候调整；
操作流程只给轻量操作；
速查只给命令。

### 2. 必要重复可以存在

不同文档为了独立使用，可以重复少量关键内容。

重复的目的必须是：
避免为了继续操作而强制跳到另一份文档。

### 3. 建立“文档影响映射”

例如：

refresh-access
→ Watcher 使用指南：权限机制 + 命令
→ 下载流程：异常分支
→ 命令速查：命令入口
→ Cleanup：无

以后代码改动先查影响映射，不必每次全文重读。

### 4. 机器事实自动抽取

可以从代码自动检查：
- argparse 命令/参数；
- config 默认值；
- SQLite schema；
- 状态枚举；
- 脚本版本。

机器检查负责【防漏事实】。

人工/AI审稿负责：
【是否讲清、是否保留历史、是否闭合因果、是否好读】。


二十七、给 P站项目的直接使用方法
==============================

P站项目不要从：
“重新写一份使用指南”
直接开始。

应先要求 AI：

1. 读取当前脚本、CLI、数据库、配置；
2. 读取所有原始说明；
3. 回顾主要开发对话/交接材料；
4. 生成“旧知识 + 新功能 + 历史事故 + 当前行为”的内容资产清单；
5. 标出待核实内容；
6. 设计结构；
7. 再写正文；
8. 写完执行 7 轮审稿；
9. 最后再生成操作流程和命令速查。

必须特别强调：

【不要把旧稿总结成更短的新稿】
【不要只凭当前代码重建历史设计原因】
【不要以“命令和参数都出现了”作为完整性的证明】
【每个重要结论必须做二级疑问检查】


二十八、最终审稿清单
==================

内容：
- [ ] 旧稿有价值的信息全部检查过？
- [ ] 最近新增功能独立检查过？
- [ ] 当前脚本命令/参数核对过？
- [ ] 数据库、状态、配置核对过？
- [ ] 产物路径和生命周期说明过？
- [ ] 历史事故和设计原因保留过？
- [ ] 已废弃行为明确区分？

解释：
- [ ] 重要概念第一次出现时足够理解？
- [ ] 是否存在话说一半、让读者继续推导？
- [ ] A/B 混合情况是否明确？
- [ ] 时间先后改变结果时是否分情况写？
- [ ] 操作后果和恢复路径是否闭合？

命令：
- [ ] 独立命令没有藏在另一命令里？
- [ ] 核心命令主要参数在入口集中？
- [ ] 无参数基础命令也明确展示？
- [ ] 关键 CLI 就地说明？
- [ ] 命令索引真的能定位章节和参数？

语言：
- [ ] 删除无意义的“不是……而是……”？
- [ ] 删除“本文怎么读”等元话语？
- [ ] 删除 AI 习惯性安全废话？
- [ ] 术语前后一致？
- [ ] 没有为了技术化使用模糊变量名？
- [ ] TXT 中重点容易扫到？

结构：
- [ ] 结构服务于用途，而不是套模板？
- [ ] 使用指南/操作流程/速查没有混成一种写法？
- [ ] 没有用“详见另一文档”省略本文件最低闭环？
- [ ] 长文有必要的目录和视觉层次？

自审：
- [ ] 已做旧知识检查？
- [ ] 已做新功能检查？
- [ ] 已做二级疑问检查？
- [ ] 已做 CLI/参数机械检查？
- [ ] 已做语言风格检查？
- [ ] 已做快速扫读检查？


结语
====

本次 B站项目文档写作最重要的经验不是“某个标题应该放哪”，而是：

【完整不等于字多，简洁不等于摘要，准确不等于只写源码字段，命令齐全也不等于文档齐全。】

长期项目文档真正需要保存的是：

当前事实
+ 使用方法
+ 操作后果
+ 历史原因
+ 异常恢复
+ 新功能。

如果读完一个重要段落后，仍必须重新问 AI：

“所以具体会怎么样？”
“那会不会重新下载？”
“这个命令现在还存在吗？”
“如果我先删再恢复呢？”
“为什么当初要这样设计？”

那么这段文档就还没有写完。
